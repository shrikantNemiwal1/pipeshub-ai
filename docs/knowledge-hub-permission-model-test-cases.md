# Knowledge Hub — Permission Model Test Cases

**Companion to** [`knowledge-hub-permission-model.md`](knowledge-hub-permission-model.md), the design doc.
Every expected result comes from its agreed parts: the decisions log (§8, cited here as D1–D72),
the rules (§3.2), placement (§3.3), target edges (§3.7) and requirements R1–R17. A case whose
outcome depends on an open question says `OPEN (Q#)` and stays open until that question is
decided — nothing is filled in by assumption.

**Status:** 2026-09-13 — 304 cases, **none** still carrying an `OPEN` marker. Every question is
answered; the implementation plan is approved.

**How this draft was made:** five reviewers drafted cases in parallel (access rules; navigation;
partitions and pagination; write path and connectors; parity, API, frontend, security, scale and
migration). Every case was then checked against the design doc: 28 duplicates were merged, and
cases that asserted something the doc leaves open were changed to `OPEN`. Notes in parentheses
about today's behaviour come from reading the code while drafting; those the open questions rely
on were re-checked against the source.

## How to read

- **IDs are stable.** Merged IDs are listed at the end of each section and are never reused.
- **Prefixes:** `AC` access rules · `NV` navigation · `PG` partitions, pagination, sorting,
filters · `DM` write path · `CN` connector-specific · `BE` backend parity · `API` contract ·
`FE` frontend · `SEC` security · `PERF` scale · `MIG` migration.
- **Pri:** `P0` must pass before merge · `P1` important · `P2` nice to have.
- **Basis:** `D#` decision · `R#` requirement · `§x.y` design-doc section · `OPEN (Q#)` open question.
- Every case runs on **both Neo4j and Arango** against the same graph (BE-01).

## Notation

- Hierarchy, parent → child: `App → RG1 → R3 → R6`. Kinds: `App` connector app, `RG` record group,
`R` record, `F` folder record, `KB` knowledge-base app, `KF` KB folder, `KR` KB record.
- Node annotations in brackets. The first is the node's `accessRule` — **one** field with three
mutually exclusive values (decision 75), not two independent flags: `O` OPEN (parents irrelevant),
`S` STRICT (every ancestor must be accessible), `R!` RESTRICTED (implies strict, and inheritance
alone is not enough — the node's own grant is required too). A node is never both `S` and `R!`;
`R!` already means strict. Then: `inh` inherits from its parent, `noinh` does not inherit, `g:U`
direct grant to the user (also `g:grp`, `g:role`, `g:org`, `g:team`), `del` deleted, `int` internal,
`ph` placeholder, `hide` hideChildren.
- User `U`, with app access `app:direct`, `app:team`, `app:grant` or `app:none`.
- Write-path edges: `NR` NODE_RELATION — `RECORD_RELATION` renamed, carrying every relationship
type, of which PARENT_CHILD and ATTACHMENT are the hierarchy (D56) — `BT` BELONGS_TO,
`IP` INHERIT_PERMISSIONS (child → parent), `RR` the old RECORD_RELATION where a case contrasts
with `main`.
- ✓ accessible, ✗ not accessible.
